## Retention and deletion state

- The code does not currently establish an approved, effective retention
  schedule. `src/core/retention_job.py` expires encrypted export snapshots and
  runs primary-data mutation only when `GDPR_RETENTION_EXECUTION_ENABLED=true`
  and current, approved per-tenant policies exist. Its implemented categories
  are messages and simulator responses. Migration 063 seeds no policy rows.
- The GDPR API supports export, durable erasure request, operation status, and
  retry flows. Erasure may remain blocked or partial while policies, uncertain
  provider activity, unstructured subject links, external deletion receipts,
  worker caches, backups, or shared authentication-account review are pending.
  It does not physically drop an organization as a single synchronous action.
- Export snapshots are encrypted, bounded, and expire after 15 minutes in the
  current implementation. This is a snapshot lifetime, not a primary-data
  retention rule.
- The DPA draft §9 says messages are retained for 90 days (soft-delete at 60,
  physical removal after a further 30) and describes derived message copies in
  logs. The current retention code instead gates content redaction on approved
  policy rows and does not implement that fixed physical-delete schedule. This
  is a material document/code mismatch to resolve before publishing or signing.
- `scripts/backup_supabase_r2.sh` implements encrypted dump upload, archive and
  digest checks, and removal of generated objects older than seven days when
  the script runs. The repository does not show an active scheduler/workflow
  invoking it. Treat R2 as a candidate only; neither an active bucket nor its
  region, lifecycle, access, or retained objects were verified. Existing
  backups are not purged by contact or tenant erasure, and restore-time
  re-erasure remains an operational decision.
- `src/core/backup/drill.py` contains a monthly loop, but its deployment and
  target configuration are not verified by repository inspection. A code path
  is not proof of a successful backup or restore drill.

## Provider and copy inventory

The repository contains adapters for Groq, OpenRouter, OpenAI-compatible
endpoints, Cerebras, and Mistral. Runtime selection is controlled by
configuration; repository code does not establish which adapter/model is
enabled in a deployment, the actual inference subprocessor behind a route, its
processing region, retention setting, training policy, or executed contract.
OpenRouter has request options to deny data collection and fallback routing;
that is a technical request setting, not independent proof of provider-side
handling.

The draft DPA also lists Meta/WhatsApp, Google Calendar/Business, Stripe,
Supabase, optional Sentry and SMTP, and Airtable/Softr propagation. Code and
drafts do not prove which integrations are active, actual data residency,
executed DPAs, transfer mechanisms, or retention configuration. The existing
Airtable/Softr deletion helpers are non-network stubs and cannot confirm
provider erasure. Confirm the deployed inventory with the responsible owner
and provider contracts before making an external statement.

Data may also exist in database backups, provider-side request logs, application
logs, email delivery, webhooks, caches, scheduled-worker state, or exports.
`docs/operations/a06-data-inventory.md` identifies known schema and export
exclusions; reconcile it against current deployment configuration and backup
objects. Do not add customer content, tokens, DSNs, or provider identifiers to
this readiness record.

## Readiness gates

1. Compare this inventory with the live deployment configuration without copying
   secrets into documentation. Record provider names, processing regions,
   account/project references, enabled integrations, and the evidence owner.
2. Have the controller and qualified reviewers resolve the decisions above and
   approve versioned policies. Do not infer approval from code defaults,
   example values, draft DPA text, or a configured feature flag.
3. Keep primary-data retention and destructive provider erasure disabled until
   their applicable approvals, barriers, worker-drain steps, evidence handling,
   and recovery paths have been reviewed.
4. For C01 schema cutover, use the separate
   [C01 preflight in #136](https://github.com/Scontismaart/Melpis/blob/a6cc7d84a8da60caa1dac6061836e7eefaf491bc/docs/operations/c01-local-preflight-20261025.md) and
   verify migration state, ACL/RLS, historical file accounting, worker
   compatibility, and a recoverable restore before production scheduling.
5. Publish no claim that a provider deletion, backup, region, retention period,
   compliance status, or restore process is active until its operational
   evidence has been reviewed and recorded by the responsible owner.
