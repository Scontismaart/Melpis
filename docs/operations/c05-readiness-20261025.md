## Application beta enrollment control

The A02 app change in [PR #178](https://github.com/Scontismaart/Melpis/pull/178)
adds an exact, case-insensitive email roster gate using
`MELPIS_BETA_ALLOWED_EMAILS` (comma-separated addresses). In `development`,
`dev`, `local`, `test`, and `testing`, self-enrollment remains available for
local work. Every other environment fails closed unless the normalized email
matches the configured roster; an unset/empty roster authorizes no new account.
The check covers public email registration, the email-confirmation completion
callback, first-time Google OAuth provisioning, first `/me` JIT provisioning,
and team-invitation creation/acceptance. Existing users retain only their
current memberships and continue through normal role/MFA authorization.

The allowlist value is operational configuration and must never be committed
or copied into this document. The code gate prevents new tenant provisioning
for an unlisted email, but does not change Supabase Auth's public self-signup
setting. The operator must verify that setting and the deployed app's roster
value before beta; an unlisted Auth identity must still fail the application's
first-tenant provisioning path. PR #178 was squash-merged as `74c46aa`; its
CI run [#43741556082](https://github.com/Scontismaart/Melpis/actions/runs/43741556082)
passed. The deployed roster and Supabase Auth self-signup setting still require
Staging verification before beta.

## Retention and deletion state

- The code does not currently establish an approved, effective retention
  schedule. `src/core/retention_job.py` expires encrypted export snapshots and
  mutates primary data only when `GDPR_RETENTION_EXECUTION_ENABLED=true` and
  current, approved per-tenant policies exist. With the newer C2.4 schema
  present, the general job exits before its ordinary message-content worker.
  SQL096 handles only eligible terminal C2.4 messages with receipt and
  verified subject-lineage fields, whether or not `deleted_at` is set; ordinary
  or legacy messages without those fields have no verified 60/90-day cleanup
  path in this snapshot. SQL074 stamps `c24_received_at` on insert and makes it
  immutable; SQL089/096 require that server receipt and verified lineage rather
  than infer message age from historical `created_at` or provider timestamps.
  No safe cleanup age is established for unlineaged legacy rows, so coverage
  remains OPEN pending trusted provenance or a reviewed remediation. The job
  also removes typed C2.4 booking proposal fields from eligible source/cache
  records.
  The product policy does not assign a simulator-response period or authorize
  a general simulator-response purge.
  Migration 063 seeds no policy
  rows. Snapshot expiry is not a customer-content schedule.
- Migrations 089 and 091 add cursor-backed C2.4 receipt/source and hotel
  lifecycle sweeps. They require the global retention flag, the C2.4 owner and
  automatic-sweep flags, a dedicated `GDPR_C24_OWNER_RETENTION_DSN`, and the
  narrow `melpis_c24_retention` identity. The scheduler does not fall back to
  the application connection. It defers held or uncertain rows and stops on
  authorization/database errors. These code paths do not prove that production
  flags, role, DSN, approved tenant policies, or a successful schedule exist.
- Migration 093 stores a short-lived C2.4 worker capability payload containing
  customer/booking and confirmation details. Its maximum five-minute authority
  lifetime is not deletion. The A06 change in
  [PR #179](https://github.com/Scontismaart/Melpis/pull/179) adds migration 094
  to scrub completed and expired payloads while retaining hashes and replay
  tombstones; it was squash-merged as `f5f5040`. Application of migration 094
  to Staging or Production is unverified. Verify its application and scheduled
  cleanup before calling this deployed behavior.
- The GDPR API supports export, durable erasure request, operation status, and
  retry flows. Erasure may remain blocked or partial while policies, uncertain
  provider activity, unstructured subject links, external deletion receipts,
  worker caches, backups, or shared authentication-account review are pending.
  It does not physically drop an organization as a single synchronous action.
- Export snapshots are encrypted, bounded, and expire after 15 minutes in the
  current implementation. This is a snapshot lifetime, not a primary-data
  retention rule.
- The approved Privacy V1.0 standard is at most 60 days of ordinary message
  availability and primary-content removal within 90 days. DPA draft §9 uses
  those same windows but describes “physical removal” and derived log copies;
  that wording could promise deletion beyond the primary database. The current
  code gates content mutation on approved tenant policy rows and does not prove
  a scheduled 90-day purge. Keep the approved periods fixed, align the draft's
  scope to primary content, and do not claim an active schedule until the
  controller/counsel approves wording and operations provides evidence.
- `scripts/backup_supabase_r2.sh` implements encrypted dump upload, archive and
  digest checks, and removal of generated objects older than seven days when
  the script runs. The repository does not show an active scheduler/workflow
  invoking it. Treat R2 as a candidate only; neither an active bucket nor its
  region, lifecycle, access, or retained objects were verified. Existing
  backups are not purged by contact or tenant erasure, and restore-time
  re-erasure remains an operational decision.
- `src/core/backup/drill.py` contains a monthly loop, but its deployment and
  target configuration are not verified by repository inspection. A code path
  is not proof of a successful backup or restore drill.
